# Report — `_rebuildGraph` diff-based (cl-node-graph)

Branch: `feat/cl-node-graph`
Commit: `84b661c53ad807e993dca7764eae0be9b483888b`

## Bug
`_rebuildGraph` rimuoveva e riaggiungeva TUTTI i nodi fl ad ogni cambiamento.
`addNode` genera un id motore nuovo ogni volta → i child widget del motore
ricevono chiavi nuove ad ogni rebuild → durante la reconciliation di Flutter il
nuovo child viene inserito prima che il vecchio sia rimosso →
`NodeEditorRenderBox.insert` (vendor `node_editor_render_object.dart:371`) vede
transitoriamente più figli dei nodi nel controller e lancia
`Found N children, but only M nodes`. Storm sotto notifyListeners multipli (N+1).

## API controller usata (`lib/src/vendor/fl_nodes/src/core/controller/core.dart`)
- `addNode(idName, {offset, customData}) -> FlNodeDataModel` (475): genera id NUOVO.
- `removeNodeById(id)` (576): rimuove il nodo e a CASCATA i suoi link
  (`removeLinkById(..., isHandled: true)`), emette `FlRemoveNodeEvent`.
- `addLink(n1, p1, n2, p2) -> FlLinkDataModel?` (618): emette `FlAddLinkEvent`.
- `removeLinkById(id)` (741): emette `FlRemoveLinkEvent`.
- `getNodeById(id) -> FlNodeDataModel?` (436).
- **Offset-update assoluto: NON esiste** metodo dedicato. `dragSelection` (944) è
  delta-based e opera sulla selezione (emette `FlDragSelectionEvent`) → inadatto.
  `FlNodeDataModel.offset` (models/data.dart:499) è però un **campo pubblico
  mutabile**, mutato direttamente dal motore stesso (core.dart:340/344/973/979).
  `unboundNodeOffsets` (424) è una Map pubblica (base del drag / snap).

## Come diffo i nodi (per clId)
1. `currentClIds = widget.nodes.map(id).toSet()`.
2. clId in `_flByCl` ma non in `currentClIds` → `removeNodeById(flId)` + drop da `_flByCl`.
3. Per ogni nodo corrente: `_clNodeById[n.id] = n` (nodeBuilder legge dati aggiornati).
   - clId PERSISTITO (`_flByCl[n.id] != null`): mantieni id motore. Aggiorna offset:
     `fl.offset = pos` + `unboundNodeOffsets[flId] = pos` (via campo pubblico —
     unico meccanismo disponibile, lo stesso usato internamente dal motore).
   - clId NUOVO: `addNode` + init `builtStyle`/`builtHeaderStyle` dal prototype
     (invariato) + record in `_flByCl`.
4. `_clNodeById.removeWhere(!currentClIds)` — prune dati stantii.

## Link / cascata bookkeeping
Ordine scelto: **rimuovo tutti i link tracciati PRIMA dei nodi.**
- Pre-registro `_edgeByFlLink.keys` in `_ownRemovedLinkIds`, poi
  `removeLinkById` su ciascuno, poi `_edgeByFlLink.clear()`.
- Così quando `removeNodeById` gira sui nodi scomparsi i loro link sono GIÀ
  spariti → nessuna cascata → niente doppie rimozioni né leak in `_edgeByFlLink`.
- Riaggiungo i link da `widget.edges` (fonte di verità), pre-registrando gli id
  in `_ownAddedLinkIds`. Semantica containment vs link identica al codice attuale.
- Guardie anti-feedback (`_ownAddedLinkIds`/`_ownRemovedLinkIds`/`isSideEffect`)
  e `_onEngineEvent` NON toccate: gli eventi async del bus vengono assorbiti come
  prima. `_applySelection()` e `setState` finali invariati.

## API pubblica / event handling / nodeBuilder / didUpdateWidget: invariati.
Modificato solo il corpo di `_rebuildGraph` + aggiunto getter test-only
`debugFlIdFor(clId)`.

## Offset dei nodi persistiti
**Si aggiornano.** `fl.offset` è mutato al nuovo layout e `unboundNodeOffsets`
tenuto in sync. `enableSnapToGrid: false` quindi `unboundNodeOffsets` conta solo
per il drag futuro; il repaint arriva dal `setState`. Non è "fake": è lo stesso
campo mutato internamente dal motore.

## Fix wave (#3 + minors)

### #3 — reposition dei nodi persistiti non propagata al render object
**Meccanismo usato.** Dopo il diff, se almeno un nodo PERSISTITO ha cambiato
`fl.offset` E non c'è stato alcun add/remove (`repositioned && !structuralChange`):
```
_controller.forceNodeRepaint();  // nodesDataDirty = true
_controller.forceLinkRepaint();  // linksDataDirty = true (archi ai nuovi offset)
_controller.eventBus.emit(FlConfigurationChangeEvent(_controller.config, id: UniqueKey().toString()));
```
**Perché.** Verificato contro il vendor:
- `node_editor_render_object.dart:155-158`: `_handleControllerEvent` instrada
  ESPLICITAMENTE `FlConfigurationChangeEvent` (oltre a `FlTreeEventCat` e
  `FlDragSelectionEvent`) verso `return _updateNodes()`. L'evento passa il guard
  di riga 137 perché mixa `FlLayoutEventCat`.
- `_updateNodes` (riga 293) early-return se `!nodesDataDirty`; `forceNodeRepaint`
  (core.dart:287) alza il flag → `_updateNodes` gira e copia `node.offset ->
  childParentData.offset` (riga 315) rilocando i nodi spostati; poi `markNeedsLayout`
  (FlLayoutEventCat, riga 198).
- `FlConfigurationChangeEvent` (events.dart:583) NON è undoable (via
  `FlConfigurationClassEvent -> super()`), non resetta viewport/transform (a
  differenza di `FlLoadProjectEvent`/`FlNewProjectEvent`, gestiti a parte riga
  187-192), non tocca clipboard (a differenza di Paste/Cut). Porta la config
  CORRENTE (`_controller.config`, core.dart:315 campo pubblico); nessun consumer
  la ri-applica → non muta lo stato del motore. Emesso UNA sola volta per rebuild.
- Se c'è stato add/remove, `FlAddNodeEvent`/`FlRemoveNodeEvent`
  (`FlTreeEventCat`, events.dart:308/338) già instradano `_updateNodes` che
  rilegge TUTTI gli offset (inclusi i persistiti spostati) → nessuna doppia
  propagazione, nessun evento config ridondante.
- Anti-crash preservato: nessun churn di id nodo (il diff resta id-stabile;
  set di nodi invariato ⇒ zero add/remove). L'evento config non aggiunge/rimuove
  child del render object.

**Da confermare su render reale (non verificabile visivamente qui).** Il bus è
`StreamController.broadcast` → consegna async (microtask) DOPO il `setState`
finale. Timing atteso: `setState` ricostruisce il widget (updateRenderObject NON
resetta offset), poi l'evento async fa girare `_updateNodes` con `nodesDataDirty`
ancora true → relayout + repaint alle nuove posizioni. Serve conferma su un
render reale (l'harness headless non carica lo shader `grid.frag`, non dipinge il
RenderBox) che: (a) tra `setState` e l'evento async nessun frame azzeri
`nodesDataDirty` prima di `_updateNodes` (l'azzeramento avviene solo DENTRO
`_updateNodes`, riga 520, quindi atteso safe), e (b) i nodi spostati risultino
ridisegnati E hit-testati alla nuova posizione dopo il reparent tra nodi
preesistenti.
